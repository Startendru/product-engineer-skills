# Токены дизайн-системы

## Зачем

Цвет в интерфейсе живёт на трёх ярусах. Внизу — **примитив**: просто значение, `#ff6a3d`,
без всякого смысла. Над ним — **семантика**: роль, то есть ответ на вопрос «что этим
красят»: заливка основной кнопки, вторичный текст, кольцо фокуса. Наверху —
**компонентный ярус**: какая роль отвечает за какое свойство какого компонента.

Ярусы нужны затем, что менять смысл и менять значение — разные операции. Пока «оранжевый»
и «цвет главного действия» — одно и то же слово, сделать главное действие темнее нельзя,
не перекрасив заодно всё оранжевое в продукте.

**Главное правило: пересчитывай, а не переписывай.**

Каждый коэффициент контраста, каждое имя цвета, каждая поверхность берутся из замера или
из кода, а не из памяти. Правдоподобное число выглядит ровно как измеренное — отличить их
чтением невозможно, поэтому проверка пересчитывает всё сама.

## Предусловие

Нужен файл **`design-system/inventory.json`** — результат предыдущего шага (его читаемый
вид лежит рядом, `inventory.md`). Из него берутся поверхности продукта: те фоны, на
которых реально лежит текст.

**Файла нет — остановитесь и скажите пользователю:** сначала нужно вызвать
**`design-system:inventory`**, иначе поверхности придётся брать из палитры, а палитра
описывает объявленное, а не то, что оказалось под буквами.

Исключение одно: проект с нуля, экранов ещё нет. Тогда поставьте в артефакте
`"greenfield": true`, и поверхности вы задаёте сами — это те фоны, которые собираетесь
завести.

## Что на выходе

Файл **`design-system/tokens.json`** — данные. Из него проверка генерирует
`design-system/tokens.md` для чтения человеком. **Оба создаёт скрипт, markdown руками не
пишется.**

Скелет — заполните своими значениями:

```json
{
  "greenfield": false,
  "primitives": {
    "rd-ink": { "$value": "#1a1a1e", "$type": "color", "origin": "existing" },
    "rd-brand-deep": { "$value": "#c8431c", "$type": "color", "origin": "new" }
  },
  "semantic": {
    "surface-canvas": { "ref": "rd-canvas", "purpose": "фон страницы", "use": "surface",
                        "usages": 880, "evidence": "app/globals.css:4" },
    "text-primary": { "ref": "rd-ink", "purpose": "основной текст", "use": "bodyText",
                      "usages": 1490, "evidence": "app/page.tsx:5", "onSurfaces": "all" }
  },
  "component": { "button.background": "action-fill", "button.label": "action-label" },
  "surfaces": [
    { "color": "#ffffff", "name": "белая простыня", "textNodes": 1240, "origin": "existing" }
  ],
  "matrix": [
    { "role": "text-primary", "surface": "#ffffff", "ratio": 17.35, "required": 4.5, "verdict": "pass" }
  ]
}
```

## Порядок работы

1. **Собрать примитивы.** Все цвета, которые в продукте уже есть, плюс те, что вводите
   сейчас. У каждого — пометка `origin`: `existing` (цвет объявлен в проекте) или `new`
   (появляется этим шагом). Пометка не формальность: проверка идёт в код и сверяет.
2. **Вывести семантические роли из фактического употребления.** Не придумать «нужные»
   роли, а посмотреть, какие смыслы уже носит палитра. Один примитив в двух ролях — это
   **две записи**, а не одна. Подробно — `references/token-tiers.md`.
3. **Построить матрицу «роль × поверхность»** и посчитать контраст каждой пары на **всех**
   поверхностях, где роль встречается. Методика, нормы и формула —
   `references/contrast-matrix.md`.
4. **Зафиксировать компонентный ярус** там, где он нужен: `button.background → action-fill`.
   Значение здесь — **всегда имя роли, никогда имя примитива.**

## Роли выводятся из употребления, а не придумываются

Разберём случай, на котором этот скилл отлаживался.

В проекте серый `#95949a` красит мелкие подписи и не проходит контраст. Соблазнительная
починка: взять цвет потемнее из тех, что уже есть в палитре, — например `#54545a`.

**Это разрушает ярус семантики.** `#54545a` — значение роли «вторичный текст», которая уже
существует. После такой правки «вторичный текст» и «приглушённая подпись» становятся одним
цветом, то есть перестают быть двумя ролями. Различие, ради которого ярус и заводили,
исчезает ровно в тот момент, когда его чинят: дальше нельзя сделать подписи светлее, не
задев описания.

Верная починка — **новый примитив** под эту роль: подписи получают собственное значение
(в том разборе — `#5c5c63`), и обе роли остаются различимыми.

Если две роли действительно должны быть одного цвета — так бывает — это записывается явно:
`"mergedWith": "<другая роль>"`. Слияние допустимо; молчаливое слияние — нет.

## Порог берётся по худшей поверхности

Один и тот же цвет на разных фонах даёт разный контраст. Подбор «по белому» даёт ложное
прохождение: тот же серый `#95949a` даёт **3.01** на белом и **2.55** на бежевом. Если в
продукте есть бежевая поверхность, цвет не подходит — независимо от того, как он выглядит
на белом.

Поэтому роль проверяется на **каждой** поверхности, где встречается, и принимается по
**худшему** результату. Сузить список поверхностей можно, только если роль там физически
не бывает, — и написать, почему (`onSurfaces` + `restrictedWhy`).

Отдельно: **заливка кнопки — тоже поверхность.** Затемнив кольцо фокуса под бежевый фон,
легко получить кольцо того же тона, что заливка кнопки, — на самой кнопке оно исчезнет.
В разборе такая пара дала контраст **1.16** при норме 3. Матрица это ловит, только если
заливка внесена в `surfaces`.

## Схема `tokens.json`

### `primitives` — сырые значения

| Поле | Смысл |
| --- | --- |
| ключ | Имя примитива. У `origin: existing` — **ровно то имя, под которым цвет объявлен в проекте** |
| `$value` | Значение, hex вида `#rrggbb` |
| `$type` | Всегда `color` |
| `origin` | `existing` — цвет уже в проекте, `new` — вводится этим шагом |

Формат `$value`/`$type` — из спецификации W3C Design Tokens; см. `references/token-tiers.md`.

### `semantic` — роли

| Поле | Смысл |
| --- | --- |
| ключ | Имя роли: что красим, а не какого оно цвета |
| `ref` | Имя примитива. Обязан существовать в `primitives` |
| `purpose` | Одной фразой: что именно этой ролью красят |
| `use` | `bodyText` (обычный текст), `largeText` (крупный), `nonText` (границы, иконки, фокус), `surface` (фон). **Определяет норму контраста** |
| `usages` | Сколько мест в продукте эту роль просят. Целое число |
| `evidence` | Файл проекта, где роль употребляется, можно со строкой: `app/page.tsx:7`. Проверка убеждается, что файл существует |
| `onSurfaces` | `"all"` либо список поверхностей, где роль бывает. Только для ролей переднего плана |
| `restrictedWhy` | Почему список сужен. Обязательно, если `onSurfaces` короче полного |
| `mergedWith` | Имя другой роли, если совпадение цвета намеренное |

### `component` — компонентный ярус

Пары `компонент.свойство → имя роли`. Значение — **всегда роль**. Примитив здесь
проверку не проходит.

### `surfaces` — поверхности продукта

| Поле | Смысл |
| --- | --- |
| `color` | Hex фона |
| `name` | Человеческое название |
| `textNodes` | Сколько текстовых узлов на нём лежит (из инвентаря) |
| `origin` | `existing` — поверхность найдена инвентаризацией, `new` — вводится этим шагом |

### `matrix` — пары «роль × поверхность»

| Поле | Смысл |
| --- | --- |
| `role` | Имя семантической роли |
| `surface` | Hex поверхности из `surfaces` |
| `ratio` | Коэффициент контраста. **Пересчитывается проверкой** |
| `required` | Норма. **Пересчитывается** из `use` роли |
| `verdict` | `pass` или `fail`. **Пересчитывается** |
| `waiver` | Причина, по которой провал принят осознанно. Без неё `fail` не проходит проверку |

## Проверка — обязательный последний шаг

```bash
node scripts/check-tokens.mjs design-system/tokens.json .
```

Второй аргумент — корень проекта, и он обязателен. Скрипт **ничего не берёт на веру**:

- пересчитывает каждый коэффициент матрицы из hex-значений и сверяет с заявленным;
- проверяет, что каждая ссылка ведёт в существующую запись, а примитив с пометкой
  «уже в проекте» действительно объявлен в коде с тем же значением;
- ловит две роли, указывающие на одно значение без пометки о намеренном слиянии;
- сверяет список поверхностей с инвентарём — пропущенная поверхность и поверхность,
  взятая из палитры вместо замера, не проходят.

При успехе скрипт перезаписывает `design-system/tokens.md` — читаемый вид для человека.

**Пока скрипт не прошёл, шаг не закрыт.** Не переходите к следующему скиллу: реестр
покрасит компоненты от этих же значений.

## Частые ошибки

| Ошибка | Как выглядит | Почему это провал |
| --- | --- | --- |
| Роли схлопнуты | «Возьмём для подписей цвет вторичного текста» | Две роли стали одной. Ярус семантики уничтожен в момент починки |
| Число названо по памяти | «Контраст падает до 2.36» при фактических 2.55 | Остальные числа в отчёте сходятся, поэтому неверное выглядит достоверным |
| Цвет назван существующим, а его нет | `rd-ink-soft-darker` в списке «проверенных цветов палитры» | Такого токена в проекте нет. Правдоподобное имя не значит существующее |
| Обоснование сочинено | «Серый выбран для декора» при авторском комментарии «моно-подписи групп» рядом | Файл прочитан, вывод написан противоположный. Обоснование берётся из кода, а не из головы |
| Проверка только на типовой поверхности | «На белом проходит, остальные похожи» | Похожие фоны дают разный контраст. Порог — по худшей поверхности |
| Норма выбрана мягче | «Это же не текст, хватит 3» про надпись на кнопке | Норму задаёт назначение роли, а не удобство результата |
| Поверхность отброшена | «Она редкая, не считается» | Именно на редкой тёмной поверхности порог обычно и проваливается |
| Компонент красится от примитива | `button.background → rd-brand-deep` | Смена смысла потребует правки каждого компонента. Ради этого ярусы и заводились |

## Дальше

Вызовите **`design-system:registry`** — он прочитает `design-system/tokens.json`, возьмёт
из него семантические роли и матрицу и разложит компоненты, паттерны и шаблоны страниц по
уровням, покрасив их от этих ролей.
