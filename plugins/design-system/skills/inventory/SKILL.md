# Инвентаризация интерфейса

## Зачем

Дизайн-систему нельзя спроектировать по тому, что в проекте **объявлено**. Проектировать
надо по тому, что **используется**. Это разные картины, и расходятся они сильно: компонент
может существовать и не иметь ни одного импорта, а половина экранов — собираться вручную
мимо него.

**Главное правило: считай использованное, не пересказывай объявленное.**

Прочитать `components/ui/*` и пересказать, что там написано, — не инвентаризация. Пока у
каждой строки нет числа, работа не сделана.

## Пропустить, если

Проект с нуля, экранов ещё нет. Тогда инвентаризировать нечего — переходите сразу к
`design-system:tokens`.

## Предусловие

Нужен доступ к браузеру (Playwright или Chrome DevTools MCP) и запущенное приложение.
Без браузера часть работы выполнить нельзя — см. «Поверхности» ниже. Если браузера нет,
скажите об этом прямо и заполните `measuredInBrowser: false` с перечнем непроверенного.

## Что на выходе

Файл `design-system/inventory.json` — данные. Из него генерируется `design-system/inventory.md`
для чтения человеком. **Оба создаёт проверочный скрипт, руками markdown не пишется.**

Скелет — заполните своими числами:

```json
{
  "project": { "root": ".", "componentsRoot": "components", "filesScanned": 0 },
  "controls": [
    { "role": "button", "totalUsages": 0, "implementations": [
      { "name": "Button", "source": "components/ui/button.tsx", "usages": 0, "files": 0 },
      { "name": "raw <button>", "source": null, "usages": 0, "files": 0 }
    ]}
  ],
  "deadComponents": [ { "source": "components/ui/select.tsx", "imports": 0 } ],
  "surfaces": [
    { "color": "#ffffff", "token": "rd-paper", "textNodes": 0, "screens": 0, "contrastFailures": 0 }
  ],
  "typeScale": { "distinctSizes": 0, "scaleTokenUsages": 0, "declared": [ { "px": 13, "occurrences": 0 } ] },
  "tokens": [ { "name": "--color-rd-muted", "value": "#95949a", "usages": 0 } ],
  "pageStructure": [ { "url": "/", "mainLandmarks": 1, "h1": 1, "headings": 0 } ],
  "outOfScope": ["components/markdown-editor/"],
  "measuredInBrowser": true,
  "notMeasured": []
}
```

Поля целиком — `references/artifact-schema.md`.

## Порядок работы

1. **Контролы.** Для каждой роли (кнопка, поле, чип, чекбокс) найти **все** реализации и
   посчитать места вызова каждой. Реализации **ищутся в коде, а не берутся из головы**:
   параллельный компонент может называться как угодно, и именно он обычно самый массовый.
   Сырая вёрстка — такая же реализация, её считать наравне. Методика —
   `references/count-controls.md`.
2. **Мёртвые компоненты.** Для каждого файла компонента посчитать импорты. Ноль импортов —
   в `deadComponents`. Этот шаг пропускают чаще всего, а он даёт самые дешёвые находки.
3. **Поверхности.** Каждый непрозрачный фон, несущий текст, с числом текстовых узлов и
   контрастом. **Только замером в браузере** — методика и слепые пятна в
   `references/measure-surfaces.md`.
4. **Шкала кеглей.** Все объявленные размеры с частотой.
5. **Структура страниц.** По экранам: число главных лендмарков, число `h1`, число заголовков.

## Проверка — обязательный последний шаг

```bash
node scripts/check-inventory.mjs design-system/inventory.json .
```

Второй аргумент — корень проекта, и он обязателен. Скрипт **пересчитывает ваши числа по
коду**: сверяет вызовы каждой реализации, ищет компоненты без единого импорта и требует,
чтобы каждый файл компонента был учтён — как реализация, как мёртвый или как вынесенный из
области системы. Отчёт, который сходится сам с собой, но не имеет отношения к проекту,
проверку не проходит.

При успехе скрипт перезаписывает `design-system/inventory.md` — читаемый вид для человека.

**Пока скрипт не прошёл, шаг не закрыт.** Не переходите к следующему скиллу.

## Частые ошибки

| Ошибка | Как выглядит | Почему это провал |
| --- | --- | --- |
| Пересказ вместо подсчёта | «Компонент `Button` имеет 7 вариантов оформления» | Описано объявленное. Сколько раз он вызван — неизвестно |
| Компонент назван рабочим без проверки импортов | Подробное описание `Select` с выпадающим списком | У файла может быть ноль импортов. Описан мёртвый код |
| Сырая вёрстка не сосчитана | В отчёте только компоненты из `components/` | Именно сырая вёрстка обычно и составляет большинство |
| Фокус описан по классу | «вермилион-граница и светлое кольцо» | Класс говорит о намерении. Виден ли индикатор — вопрос замера |
| Поверхности взяты из палитры | Список токенов из файла темы | В палитре объявлено одно, под текстом лежит другое |
| Реализации перечислены по памяти | Посчитаны `Button` и `<button>`, а форк рядом не найден | Именно форк обычно и есть большинство вызовов. Реализации ищут в коде |
| Роль без нативного тега посчитана по `<div>` | «сырая карточка: 511» | В проекте сотни `div`, и ни один не «сырая карточка». Считать по тегу можно только роли с нативным эквивалентом |

## Дальше

Вызовите **`design-system:tokens`** — он прочитает `surfaces` из вашего `inventory.json` и
построит по ним матрицу контраста.
