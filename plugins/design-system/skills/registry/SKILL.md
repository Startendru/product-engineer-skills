# Реестр дизайн-системы

## Зачем

Реестр отвечает на три вопроса разом: **из чего система состоит**, **чего в ней нет** и **какие
правила обязательны для всех**. Без него разговор о дизайн-системе остаётся разговором: каждый
называет системой свой набор файлов, а недостающее не называет вообще.

Два главных правила скилла:

1. **`missing` записывается, а не строится.** Отсутствие, не записанное явно, через месяц
   неотличимо от «не нужно».
2. **Каталог покрывает типичную дизайн-систему целиком**, а не только то, что нашлось в вашем
   проекте. Иначе система молча наследует пробелы продукта, на котором её собирали.

## Предусловие

Нужен файл **`design-system/tokens.json`** от предыдущего шага. Компоненты красятся от
семантических ролей, а не от сырых значений, — значит токены заводятся раньше реестра.

**Файла нет — остановитесь и скажите пользователю: сначала нужно вызвать
`design-system:tokens`.** Проверка это же условие проверяет машинно и без `tokens.json` не
запускается.

Инвентаризация (`design-system:inventory`) не обязательна, но если она есть — берите из
`inventory.json` состав реализаций и числа вызовов: половина реестра уже посчитана там.

## Что на выходе

| Файл | Что это |
| --- | --- |
| `design-system/registry.json` | Данные. Машиночитаемый файл, который прочитают витрина и внедрение |
| `design-system/registry.html` | **Просмотр для человека.** Собирается проверкой, открывается двойным щелчком |
| `design-system/patterns/*.md` | Три файла каталога паттернов на русском: `cross-cutting.md`, `flows.md`, `page-templates.md` |

Скелет `registry.json` — заполните своими записями:

```json
{
  "project": { "root": ".", "componentsRoot": "components" },
  "outOfScope": ["components/markdown-editor/"],
  "entries": [
    {
      "id": "button",
      "title": "Кнопка",
      "level": "atom",
      "status": "draft",
      "description": "Основной контрол действия.",
      "adoption": { "migrated": 29, "total": 229 },
      "impl": {
        "component": "Button",
        "source": "components/ui/button.tsx",
        "nativeTag": "button",
        "alternatives": ["RegisterButton", "FilterChip"]
      },
      "variants": ["основная", "второстепенная", "опасная"],
      "states": ["обычное", "наведение", "фокус", "выключено", "загрузка"],
      "a11y": "видимый индикатор фокуса, доступное имя у иконочного варианта",
      "tokensUsed": ["action.background"],
      "usedOn": ["app/(learn)/profile/profile-ui.tsx"],
      "note": "200 вызовов из 229 идут мимо компонента",
      "blockedBy": null
    }
  ]
}
```

Поля целиком, шесть уровней и три статуса — `references/atomic-levels.md`.

## Три вида записей

| Вид | Уровни | Что описывает |
| --- | --- | --- |
| Компоненты | `foundation`, `atom`, `molecule`, `organism` | Материал системы и её детали. У каждого — статус и доля внедрения |
| Паттерны | `pattern` | Сквозные правила и повторяющиеся решения. Не файлы, а договорённости |
| Шаблоны страниц | `template` | Правила уровня страницы целиком |

**Шаблоны страниц существуют потому, что этот класс дефектов недоступен библиотеке
компонентов.** Кнопка не знает, сколько на странице главных лендмарков, а поле ввода не знает,
сколько на ней заголовков первого уровня. Два `main` и два `h1` — дефекты, которые нельзя
починить внутри компонента: их можно записать только здесь.

## Каталог паттернов — 29 позиций

| Справочник | Паттерны | О чём |
| --- | --- | --- |
| `references/cross-cutting.md` | 1–10 | Обязательны для **каждого** компонента: фокус, состояния, размер цели, имя, цвет, движение, обрезка, цифры, иконки, выравнивание индикаторов |
| `references/flows.md` | 11–22 | Повторяющиеся решения: формы, ошибки, таблицы, пустые состояния, загрузка, окна, уведомления, подтверждения, поиск, навигация, файлы |
| `references/page-templates.md` | 23–29 | Уровень страницы: каркас, заголовки, поверхности, шапка экрана, типовые экраны, точки перелома, мера строки |

Каждый паттерн попадает в реестр записью со своим `id` из справочника. **Если такого случая в
вашем продукте нет — запись всё равно заводится, со статусом `missing` и причиной.** Проверка
сверяет все 29 по именам и падает, если хоть одного нет.

Заодно перенесите три справочника в `design-system/patterns/` целевого проекта: там они станут
документом команды, а не частью скилла.

## Порядок работы

1. **Прочитать `tokens.json`** — из него берутся семантические роли для поля `tokensUsed`.
2. **Найти компоненты в коде, а не по памяти.** Пройти папку компонентов файл за файлом. Форк,
   через который идёт большинство вызовов, обычно называется не так, как ожидаешь, — и именно
   его пропускают. Каждый файл компонента обязан попасть либо в запись, либо в `outOfScope`.
3. **Посчитать долю внедрения** на каждый компонент: `migrated` — вызовы канонического
   компонента, `total` — они же плюс вызовы форков из `impl.alternatives` плюс сырая вёрстка по
   `impl.nativeTag`.
4. **Записать недостающее.** Что нужно типичному продукту, но в системе отсутствует, — запись
   со статусом `missing` и причиной.
5. **Завести все 29 паттернов** по трём справочникам.
6. **Прогнать проверку** — она же соберёт `registry.html`.

## Проверка — обязательный последний шаг

```bash
node scripts/check-registry.mjs design-system/registry.json . design-system/tokens.json
```

Второй аргумент — **корень проекта, и он обязателен**. Проверка не верит заявленным числам: она
пересчитывает вызовы каждого компонента по коду, убеждается, что названный файл существует и
компонент из него действительно экспортируется, что каждый форк встречается в коде, что
`missing` не поставлен существующему компоненту, что `ready` не стоит при неполном внедрении и
что все 29 паттернов на месте. Реестр, сходящийся сам с собой и не имеющий отношения к
проекту, проверку не проходит.

При успехе она перезаписывает `design-system/registry.html`.

**Пока проверка не прошла, шаг не закрыт.** Витрина и внедрение прочитают тот же файл и упрутся
в те же дыры.

## Показывать просмотр, а не исходник

Последнее действие скилла — **назвать пользователю путь к `design-system/registry.html`** и
сказать, что файл открывается двойным щелчком, без сборки и сервера.

Реестр не показывают в json. Он оптимизирован под машину именно затем, чтобы человеку
досталась читаемая страница: разделы по уровням, фильтр по статусу, доля внедрения полосой и
числом, причина у каждой записи `missing`.

## Частые ошибки

| Ошибка | Как выглядит | Почему это провал |
| --- | --- | --- |
| Перечислено только существующее | В реестре 12 записей, все `ready` или `draft` | Реестр без `missing` — опись имущества, а не карта работ |
| Статус завышен | `ready` у компонента, мимо которого идут 200 вызовов | Правка в нём не доедет до продукта. `ready` ниже 100% запрещён |
| Каталог урезан по проекту | «Таблиц у нас нет, паттерн пропустим» | Первый же появившийся случай будет решён с нуля |
| Компоненты названы по памяти | Записан `Button`, форк с сотней вызовов не найден | Самая массовая реализация обычно и есть форк. Компоненты ищут в коде |
| Правила уровня страницы потеряны | «Это не про компоненты, значит не в реестр» | Их некуда больше записать: компонент их не видит |
| Пользователю показан json | «Реестр готов, посмотрите `registry.json`» | Артефакты набора не читают в исходнике |

## Дальше

Реестр готов. Дальше два шага, **и они идут параллельно** — друг от друга не зависят:

- **`design-system:showcase`** — живая витрина и заслон в CI. Прочитает `registry.json` и
  `tokens.json`: покажет каждую запись карточкой, а `missing` — заглушкой с причиной.
- **`design-system:adopt`** — перевод продукта на систему. Прочитает `registry.json` и будет
  обновлять в нём поля `adoption` по мере миграции.
