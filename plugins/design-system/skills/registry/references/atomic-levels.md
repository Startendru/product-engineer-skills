# Уровни реестра, статусы и схема записи

Реестр — это список того, из чего состоит дизайн-система: что в ней есть, чего в ней нет и
какие правила обязательны для всех. Он лежит в `design-system/registry.json` и **читается
через `design-system/registry.html`**, а не в исходнике.

## Шесть уровней

| Уровень | Что это | Примеры |
| --- | --- | --- |
| `foundation` | Основания — не компоненты, а материал, из которого всё сделано | Палитра и токены, шкала кеглей, сетка и отступы, набор иконок, радиусы и тени |
| `atom` | Самый мелкий самостоятельный контрол. Дальше делить нечего | Кнопка, поле ввода, чекбокс, чип, значок, ссылка, аватар |
| `molecule` | Несколько атомов, собранных ради одной задачи | Поле с подписью и ошибкой, строка поиска, пара кнопок в футере окна |
| `organism` | Самостоятельный кусок экрана с собственным поведением | Таблица, модальное окно, шапка, боковая навигация, форма целиком |
| `pattern` | Правило или повторяющееся решение. Не файл, а договорённость | Индикатор фокуса, пустые состояния, подтверждение опасного действия |
| `template` | Правило уровня страницы целиком | Один главный лендмарк на странице, единственный `h1`, точки перелома |

Порядок в просмотре именно такой: сначала материал, потом детали, потом сборки, потом
правила. Читать сверху вниз — значит идти от «из чего» к «по каким законам».

### Почему `foundation` спереди, а `pattern` вместо `pages`

Классический Atomic Design начинается с атомов и заканчивается страницами. На практике обе
границы оказались неудобными, и крупные системы сдвинули их одинаково.

- **Спереди не хватает уровня.** Цвет, кегль и отступ — не компоненты, но именно они
  задают всё остальное. Shopify Polaris и GOV.UK Design System выносят их в отдельный
  раздел оснований.
- **Сзади уровень «страницы» не работает.** Страниц в продукте сотни, описывать каждую
  бессмысленно. А правила, общие для всех страниц, описать надо. Поэтому вместо «страниц»
  ставится `pattern` — правило, применимое ко многим экранам, — и `template` для правил
  уровня страницы целиком.

### Атом или молекула — как решить

Вопрос один: **можно ли выкинуть часть и оставить смысл?**

Из кнопки нельзя выкинуть ничего — останется пустое место. Кнопка — атом. Из «поля с
подписью и текстом ошибки» можно убрать ошибку, и поле с подписью останется рабочим. Значит
это сборка — молекула.

Если сомневаетесь между молекулой и организмом: у организма есть **собственное поведение**,
которое живёт без окружения. Таблица сама сортирует и разбивает на страницы, модальное окно
само ловит фокус и закрывается по Escape. Молекула ничего не решает, она только собрана.

Ошибка уровнем выше или ниже — не катастрофа: она меняет раздел в просмотре и ничего
больше. Пропущенная запись — катастрофа, потому что её никто не увидит.

## Три статуса

| Статус | Что значит | Обязательные поля |
| --- | --- | --- |
| `ready` | Компонент готов **и все места в продукте им пользуются** | `adoption`, где `migrated` равно `total` и `total` больше нуля |
| `draft` | Есть, но недоделан либо внедрён не везде | `note` — что именно мешает считать готовым |
| `missing` | Этого в системе нет | `note` — почему нет и что вместо него сейчас |

**`ready` при доле внедрения ниже 100% запрещён.** Это не пожелание — проверка роняет
такую запись. Компонент, мимо которого идут четыре вызова из пяти, не готов, как бы хорошо
он ни был написан: правка в нём не доедет до продукта.

Статус говорит о **зрелости компонента**, доля внедрения — о **состоянии продукта**. Это
два разных факта, поэтому доля живёт отдельным полем, а не прячется внутрь статуса.

## `missing` записывается, а не строится

Самое неочевидное правило реестра, и оно же главное.

Если в системе нет таблицы, в реестре появляется запись «Таблица, `missing`, причина:
таблицы собираются вручную на трёх экранах, общего компонента нет». Задача — не построить
её сейчас, а **записать, что её нет**.

Почему это важно: **отсутствие, не записанное явно, неотличимо от «не нужно».** Через месяц
никто не вспомнит, таблицы нет по недосмотру или потому, что решили обойтись. Реестр без
записей `missing` перестаёт быть картой работ и превращается в опись имущества.

Признак здорового реестра — в нём **есть** записи `missing`. Реестр, где всё `ready`, почти
наверняка неполон.

## Схема `registry.json`

Файл — объект с тремя частями:

```json
{
  "project": { "root": ".", "componentsRoot": "components" },
  "outOfScope": ["components/markdown-editor/"],
  "entries": [ ... ]
}
```

| Поле | Смысл |
| --- | --- |
| `project.root` | Корень проекта, от которого считаются все пути |
| `project.componentsRoot` | Папка компонентов. По умолчанию `components` |
| `outOfScope[]` | Что осознанно не входит в систему. Файл — точным путём, папка — с косой чертой на конце |
| `entries[]` | Записи реестра, см. ниже |

### Поля записи

| Поле | Тип | Обязательно | Смысл |
| --- | --- | --- | --- |
| `id` | строка | да | Короткое латинское имя, уникальное: `button`, `focus-indicator` |
| `title` | строка | да | Название по-русски: «Кнопка», «Индикатор фокуса» |
| `level` | строка | да | Один из шести уровней |
| `status` | строка | да | `ready`, `draft` или `missing` |
| `description` | строка | да | Одно-два предложения: что это и когда применяется |
| `adoption` | объект либо `null` | да | `{ migrated, total }` — сколько мест уже пользуются и сколько всего. `null` допустим только при статусе не `ready` |
| `impl` | объект либо `null` | для уровней `atom`, `molecule`, `organism` | Привязка к коду, см. ниже |
| `variants[]` | массив строк | нет | Варианты оформления: «основная», «второстепенная», «опасная» |
| `states[]` | массив строк | нет | Состояния: «обычное», «наведение», «фокус», «выключено», «загрузка» |
| `a11y` | строка | нет | Что требуется для доступности этой записи |
| `tokensUsed[]` | массив строк | нет | Семантические роли из `tokens.json`, которыми красится запись. Проверка сверяет каждую с разделом `semantic` |
| `usedOn[]` | массив строк | нет | Где применяется. **Пути к файлам проекта** — проверка требует, чтобы каждый существовал |
| `note` | строка | при `draft` и `missing` | Почему не `ready`, что мешает |
| `blockedBy` | строка либо `null` | нет | `id` другой записи, без которой эту не сделать |

### `impl` — привязка к коду

```json
"impl": {
  "component": "Button",
  "source": "components/ui/button.tsx",
  "nativeTag": "button",
  "alternatives": ["RegisterButton", "FilterChip"]
}
```

| Поле | Смысл |
| --- | --- |
| `component` | Имя компонента в разметке. `null`, если компонента ещё нет |
| `source` | Файл компонента. `null`, если компонента ещё нет |
| `nativeTag` | Нативный тег той же роли: `button`, `input`, `select`, `textarea`, `a`, `form`, `table`, `dialog`, `label`. `null`, если у роли нативного тега нет |
| `alternatives[]` | **Форки, живущие в коде рядом.** Другие компоненты той же роли, через которые до сих пор идут вызовы |

`alternatives` — не формальность. Самый частый провал реестра: канонический компонент
записан, а параллельная реализация, через которую идёт большинство вызовов, не найдена.
Проверка считает вызовы каждого имени из этого списка и падает, если названный форк в коде
не встречается ни разу либо если сумма не сходится с `adoption.total`.

**У роли без нативного тега** (карточка, алерт, вкладки) ставьте `nativeTag: null`. Считать
такие роли по `<div>` бессмысленно: в проекте сотни `div`, и ни один из них не «сырая
карточка».

## Что проверка пересчитывает по коду

Проверка **не верит заявленным числам**. Она принимает корень проекта и считает сама.

| Проверка | Какую ошибку закрывает |
| --- | --- |
| `impl.source` существует на диске | Компонент, которого в проекте нет |
| `impl.component` действительно экспортируется из `impl.source` | Имя угадано, а не найдено |
| `adoption.migrated` = число вызовов `impl.component` в коде | Завышенная доля внедрения |
| `adoption.total` = вызовы компонента + форков + нативного тега | Знаменатель, подогнанный под желаемую долю |
| Каждый `alternatives[]` встречается в коде хотя бы раз | Выдуманный форк |
| У `status: missing` файла в коде нет | «Нет в системе» про существующий компонент |
| У `status: ready` доля равна 100% и `total` больше нуля | Готовность, объявленная авансом |
| Компонент без единого импортёра не может быть `ready` | Мёртвый код, записанный как готовый |
| Каждый файл компонента учтён: запись, `outOfScope` либо явный пропуск | Пропущенная реализация — главная потеря реестра |
| Все 29 паттернов каталога присутствуют по `id` | «В проекте нет таблиц, пропустим» |
| Пути в `usedOn[]` существуют | Ссылки, выглядящие достоверно и никуда не ведущие |
| Роли из `tokensUsed[]` есть в `tokens.json` | Выдуманный токен |
| `blockedBy` указывает на существующую запись | Ссылка на запись, которой в реестре нет |

Последние две — самые ценные. Первая не даёт системе унаследовать пробелы проекта, на
котором её собирали. Вторая ловит то, что чтением глазами не ловится вовсе: ссылка на файл
и число выглядят одинаково убедительно независимо от того, измерены они или сочинены.

## Как запускается

```bash
node scripts/check-registry.mjs design-system/registry.json <корень проекта> [design-system/tokens.json]
```

Третий аргумент необязателен: по умолчанию `tokens.json` ищется рядом с реестром. Если его нет,
проверка не начинается вовсе и называет шаг, который надо вызвать, — `design-system:tokens`.

Код возврата `0` — прошло, и `registry.html` пересобран рядом с реестром. Код возврата `1` — не
прошло, замечания напечатаны построчно.

Просмотр можно собрать и отдельно, без проверки:

```bash
node scripts/build-registry-html.mjs design-system/registry.json
```

Но собранный проверкой просмотр надёжнее: он гарантированно сделан из файла, который проверку
прошёл.
