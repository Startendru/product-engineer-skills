# design-system

Пять скиллов, которые ведут проект от «экраны есть, системы нет» до живой дизайн-системы
с заслоном в CI.

Дизайн-система здесь — не документ и не библиотека компонентов, а **связка из трёх вещей**:
токены, от которых всё красится; реестр того, из чего система состоит и чего в ней ещё нет;
правила, обязательные для всех компонентов и страниц. Плюс два способа это увидеть и
проверка, которая не даёт правилам отъехать.

## Установка

```
claude plugin marketplace add Startendru/product-engineer-skills
claude plugin install design-system@startend
```

## Цепочка

Скиллы сцеплены жёстко: каждый проверяет артефакт предыдущего шага и отказывается
работать без него.

| Скилл | Предусловие | Что выпускает | Дальше |
| --- | --- | --- | --- |
| `design-system:inventory` | есть код с интерфейсом | `design-system/inventory.md` | `tokens` |
| `design-system:tokens` | `inventory.md` либо проект с нуля | `design-system/tokens.json` | `registry` |
| `design-system:registry` | `tokens.json` | `registry.json`, `registry.html`, `patterns/` | `showcase` и `adopt` |
| `design-system:showcase` | `registry.json` | витрина `/design-system`, заслон в CI | `adopt` |
| `design-system:adopt` | `registry.json` | обновлённая доля внедрения | следующая пачка |

`showcase` и `adopt` идут параллельно — оба питаются от реестра и друг от друга не зависят.

## Что нужно, а что нет

**Проект с нуля** пропускает `inventory` и `adopt`: инвентаризировать нечего и мигрировать
нечего. Цепочка короче — `tokens → registry → showcase`.

**Стек.** Четыре скилла нейтральны и работают где угодно. `showcase` строит витрину и
заслон под Next.js и Tailwind; на другом стеке его можно читать как описание, но код он не
выпустит.

**Браузер.** `inventory` требует Playwright или Chrome DevTools MCP: часть замеров по
исходникам недостоверна — фактическая поверхность под текстом определяется вложенностью, а
не объявлением в CSS.

## Что появляется в проекте

```
design-system/
  inventory.md      факты: сколько чего, какие поверхности, какая шкала
  tokens.json       три яруса токенов и матрица контраста
  registry.json     из чего система состоит и чего в ней нет
  registry.html     то же самое, но для человека — открывается двойным щелчком
  patterns/         правила, обязательные для всех компонентов и страниц
```

**Ни один из этих файлов не нужно читать в исходнике.** У `registry.json` есть
html-просмотр, `patterns/` — обычный текст на русском.

## Два просмотра, и они не дублируют друг друга

| | Что показывает | Когда появляется |
| --- | --- | --- |
| `registry.html` | Состав системы: записи, статусы, доля внедрения, правила | Сразу, на любом стеке |
| Витрина `/design-system` | Живые компоненты в вариантах и состояниях | Позже, только Next |

## Три правила, на которых всё держится

**Отсутствующее записывается, а не пропускается.** Компонент, которого нет, получает
статус `missing` и причину. Отсутствие, не записанное явно, через месяц неотличимо от
«не нужно».

**Статус `ready` запрещён, пока не мигрировано 100% мест.** Иначе реестр напишет «кнопка
готова», а большинство экранов продолжат использовать старую — так дубль компонента живёт
в продукте годами: он не спрятан, его просто нигде не видно.

**Порог контраста берётся по худшей поверхности, а не по типовой.** Цвет, подобранный на
белом фоне, проваливается на бежевом — и проверка при этом показывает «норма».
